# 已知不足与 V2 路线

## 当前版本的真实不足

1. **前端工程化不足。** 页面使用原生 HTML/CSS/JavaScript，多个页面文件超过数百行，组件、状态和样式复用有限。
2. **后端职责偏重。** 部分 Controller 同时承担验证、业务处理、DTO 拼装和文件操作，状态与驳回原因存在字符串编码。
3. **授权策略分散。** JWT 已引入，但 Spring Security 入口规则仍宽松，授权主要靠 Controller 手动判断，容易遗漏。
4. **自动化测试不足。** 当前只有 Spring 上下文 smoke test；主要依靠手工 API/E2E 联调和检查清单。
5. **可复现部署不足。** 原始材料缺少数据库迁移、Docker、Nginx/systemd 配置和完整部署脚本。
6. **依赖外部 CDN。** Bootstrap、Three.js、字体和 SheetJS 依赖外部网络，离线可用性和供应链控制不足。
7. **没有实时推送。** 多角色状态在下一次请求或刷新时同步，不是 WebSocket 实时协作。
8. **规模与性能证据仍需完善。** 后续正式使用阶段实际服务 237 名代表，但当前依据为项目负责人确认，仍待补脱敏聚合证明；同时没有峰值在线、并发压测或性能基准数据。
9. **Agent 尚未进入产品。** 当前只能证明 AI 辅助研发，不能宣称具备 Agent 产品能力。

## 为什么不直接覆盖第一版

第一版是能力成长的历史基线。直接用新技术重写并替换它，会失去最有价值的学习轨迹。V2 应作为独立版本，与 v1 的业务模型、缺陷和改进指标建立可比较关系。

## Python V2 建议架构

- FastAPI + Pydantic：明确请求、响应和验证边界。
- SQLAlchemy + Alembic：建立可审查的数据访问层和版本化迁移。
- PostgreSQL 或 MySQL：根据实际部署环境选择，不为换技术而换数据库。
- 模块化单体：按身份、代表团、报名、审核、付款和通知划分域，暂不引入不必要的微服务。
- pytest + API 集成测试：覆盖角色权限、状态流、文件上传和失败路径。
- Docker Compose + CI：提供本地可复现环境和最小发布门禁。
- 结构化日志、错误追踪和备份恢复演练。

## 可验证的 Agent 场景

Agent 不应直接访问或自由输出报名者 PII，也不应自动做录取、终审等高影响决定。优先考虑低风险、可审核的管理辅助：

- 报名信息完整性检查与缺失字段提示。
- 面向聚合数据的自然语言进度查询。
- 重复记录、异常状态和流程阻塞提示。
- 根据结构化状态生成通知草稿，发送前由人工确认。
- 汇总内测反馈并关联到任务、版本和验证记录。
- 给出会场分配建议，但保留规则解释、人工审批和操作日志。

## 评估方式

V2 不以“接入模型”作为完成标准，而以任务成功率、事实准确率、权限越界率、人工纠错成本、响应时间和用户采纳情况评估。所有 Agent 操作必须记录输入来源、使用的数据范围、输出、人工决定和最终副作用。

以上全部是规划，不是当前版本已经实现的能力。
