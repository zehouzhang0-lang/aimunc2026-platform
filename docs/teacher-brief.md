# AIMUNC 2026 项目说明

## 一句话概述

AIMUNC 2026 是一个面向约 250–300 人规模模拟联合国会议设计的报名与信息管理平台，覆盖代表、领队和管理员三类角色。我作为唯一的人类开发者，独立承担产品梳理、前后端开发、管理端设计、测试、部署与迭代；社团成员参与业务规则和运营需求讨论，Claude 参与架构讨论、编码辅助和审计。

## 为什么开发这个项目

大型学生会议需要持续收集参与者资料、代表团关系、志愿选择、审核状态与付款凭证。若主要依赖表格和聊天工具，信息会分散在不同人员与文件中，组织方难以形成统一视图，参与者也很难及时理解自己的处理状态。

我将这一问题抽象为三类用户旅程和一个共享数据源：代表负责提交和查看个人记录，领队负责建团、邀请和初审，管理员负责全局统计、终审、会场分配与付款审核。三类角色通过 REST API 读写同一数据库，从而减少人工转录并保持业务状态一致。

## 我的具体贡献

- 与社团沟通会议运营流程，将需求转化为页面、字段、角色和状态约束。
- 设计用户、代表团和代表报名三类核心数据实体及关联关系。
- 使用 Java 17、Spring Boot、JPA、MySQL 完成后端与约 20 个 REST 接口。
- 使用 HTML、CSS、原生 JavaScript 完成 9 个业务页面，并进行响应式适配。
- 重点设计管理员双视图、统计、筛选排序、分页、终审、会场分配、付款审核和 Excel 导出。
- 完成手工 API/E2E 联调、问题复现、部署与基于反馈的迭代。
- 使用 Claude 辅助任务拆解、实现建议、错误定位和代码审计，由我负责需求取舍、整合、验证和最终交付。

除产品与运营讨论外，没有其他人直接参与代码开发。

## 工程结果

项目在 2026-01-19 至 2026-03-17 期间从 v0.1 迭代至 v3.5，形成约 15 个主要 Java 文件、9 个业务页面、20 个 REST 接口和约 1.16 万行文本的可运行系统。系统完成 VPS、Cloudflare、Nginx 和 systemd 部署，并通过小范围内测收集到 8 项反馈，用于移动端体验、付款流程、主题系统和安全边界的后续改进。

上述 250–300 人是系统的目标会议规模，不是已经验证的真实用户量。现有证据不足以证明 200+ 人正式使用，因此展示材料不会这样表述，也不会公开任何真实报名数据。

## 最有代表性的设计

管理端是本项目最能体现产品与工程结合的部分。管理员可以在代表和代表团两种视角之间切换，查看统计指标，通过状态、志愿、会场和付款条件筛选数据，执行终审与会场分配，并按当前筛选结果导出 Excel。它把原本分散的报名记录转化为可操作的会务工作台。

另一项关键设计是跨角色状态流：代表提交后进入待审状态，领队完成初审，管理员完成终审和会场分配，代表再次查询时获得最新状态。这里的联动依赖共享数据库和请求刷新，而非 WebSocket 实时推送。

## AI 使用方式

该平台不是 Agent 产品。Claude 在开发过程中承担过“架构讨论者”和“代码助手”的角色，协助拆解任务、提出实现方案、定位错误和审计跨文件改动。我负责业务判断、架构取舍、代码整合、测试和部署，并在 AI 方案造成回归时进行回退与修正。

这段经历使我认识到：AI 可以加快陌生领域的学习和实现，但开发者仍需对上下文、边界、验证和结果负责。这也是我希望继续研究 Agent 应用和 AI 产品的原因。

## 不足与反思

作为第一个独立项目，当前版本存在明显技术债：原生前端页面较大、控制器职责偏重、自动化测试只有上下文 smoke test、数据库迁移和一键部署材料缺失，鉴权仍主要分散在 Controller 层。项目没有产品内 Agent，也没有经过大规模真实流量验证。

我选择保留并说明这些不足，因为它们能够构成真实的学习基线。这个项目的价值不是证明第一版已经完美，而是证明我能够把一个实际组织问题推进到可运行、可部署、可反馈迭代的完整系统，并能在事后进行严肃的工程复盘。

## 后续方向

后续计划保留 Java/Spring v1 作为历史基线，以 Python/FastAPI、类型化数据模型、数据库迁移和系统化测试构建 V2。在此基础上，再评估对管理者真正有用且可控的 Agent 场景，例如报名完整性检查、异常提示、聚合进度问答和通知草稿生成。所有 AI 操作都应受到权限、脱敏、人工确认与审计日志约束。

这一路线与我的 Agent 应用开发、AI 产品经理和 FDE 方向相连：理解真实工作流、与使用者共同定义问题、完成工程落地，并对系统边界和结果负责。
